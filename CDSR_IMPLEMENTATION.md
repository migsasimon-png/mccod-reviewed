# CDSR stakeholder review

## Repository audit and implementation matrix

The React and Ant Design client uses MobX and the DHIS2 app runtime. DHIS2 owns the event schema, session authentication, organisation-unit access and data-value APIs. This checkout has development proxies and no application-owned database, production API server, or job runner. CDR uses program `EIdLkJfyJ6s` and stage `lLO6f44xh4H`. The report and export components are oriented toward legacy MCCOD records.

The requested MCH017/MCH020 skip-logic guide was absent from the workspace and supplied attachments. The repository includes MCH017/MCH020 HTML forms and a separate CDR form document. The supplied summary informs scope. Its option codes must be verified against the original guide and deployed metadata before changing either workflow.

## Migration strategy

Treat DHIS2 stage metadata as schema. Export it and verify restoration against a staging copy before any import. Allocate new UIDs only for genuinely new concepts, keep all existing codes and associations, and test both historical events and new synthetic cases. Roll back the application independently of the metadata. Keep any new elements and their saved values attached until an authorised retention and compatibility plan exists.

## DHIS2 metadata migration and deployment

1. Record the target DHIS2 version and export the current CDSR program with dependencies using its program metadata endpoint. Take a verified database backup, restore it in a controlled environment and confirm that historical review and certification UIDs and values are readable. [DHIS2 metadata export and import documentation](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/metadata.html)
2. Use [the CDSR metadata contract](src/forms/childReviewMetadata.json) to prepare a target-specific additive metadata export. For each approved element, verify semantic equivalence first and reuse an existing UID when equivalent. Otherwise allocate an approved new UID. Bind only the intended elements to stage `lLO6f44xh4H` with the exact codes, types, and option codes in the contract. Leave them optional at the stage level so existing events and drafts remain editable. Keep the legacy fields and option sets. Age switches on as a set of five elements. Admission timestamp and canonical stay minutes switch on as a pair. Growth assessment prompts require mapped stabilization, ward and appropriateness controls. Deploying the client before the corresponding metadata leaves the mapped controls unavailable.
3. Validate the candidate metadata import on staging using the instance-version equivalent of `importMode=VALIDATE`. Review existing sharing, audit and record export settings before enabling any NIN fields. Add any required direct-API validation on the supported server before enabling independent writes. Confirm that neither the maternal nor the perinatal program is in the migration. This checkout has no approved target export or UID allocation, so no instance-specific import or production database changes were executed.
4. Build the application using the repository's production build script and publish through the existing DHIS2 app deployment process to staging. Run the scenarios below for both mapped and unmapped metadata using synthetic records. Verify facility scope using separate users. Run a separate migration and import review before production.
5. Roll back the application to the previous deployed package if required. Retain newly persisted values and stage attachments. Reverse metadata changes individually only after identifying all events using the affected values and verifying that they remain accessible. Use database restoration through the deployment team's incident procedure when needed.

### API and storage

The application uses its existing DHIS2 stage and data element reads and the event create/update resource. New scalar fields map to separate `dataValues` entries. Drafts use `ACTIVE` and completed reviews use `COMPLETED`. A draft never creates a certificate. Final save retains the existing MCCOD path when a cause was entered. The review list reads event status and last-update timestamps. The WHO coding widget continues to use the configured existing ICD service and release. No new external clinical endpoint is called.

Changed code is in [DynamicForm.tsx](src/components/DynamicForm.tsx) and [MccodTableSection.tsx](src/components/MccodTableSection.tsx) for the entry form, interval controls and facility status. [DynamicFormStore.ts](src/forms/DynamicFormStore.ts) owns stage binding and event persistence. [childReview.ts](src/forms/childReview.ts), [skipLogic.ts](src/forms/skipLogic.ts) and [layouts.json](src/forms/layouts.json) own derivation, visibility, validation and ordering. [registry.ts](src/forms/registry.ts) and [types.ts](src/forms/types.ts) define the review status column. Automated coverage is in [childReview.test.ts](src/forms/childReview.test.ts), [DynamicFormStore.test.ts](src/forms/DynamicFormStore.test.ts) and [App.test.tsx](src/App.test.tsx).
